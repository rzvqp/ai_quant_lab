## §2 — Commit A: request-scoped time · PASS
**Old defect (reproduced in the code history):** `TowerDependencies.now` was captured once at construction (`int(time.time())`) and reused, so N2/N3/N4 went `DATA_STALE` after ~10 min (M5) / ~30 min (M15) / ~2 h (H1), recovering only on restart. **Fix verified:** the `now` field is **removed**; `wall_clock_provider` is called **fresh per request** and is used ONLY for health/latency/staleness reporting (`wall_clock.py`'s own docstring forbids using it for data selection). `_query_tower_chain` now takes `event_as_of` (the bar being evaluated) + `data_cutoff`, with **`data_cutoff = min(data_cutoff, event_as_of)`** (no future data). Clock rollback → `WALL_CLOCK_ROLLBACK_DETECTED` (fail-closed, `MonotonicWallClock` raises `ClockRollbackError`); `event_as_of > wall_clock_now` → `FUTURE_EVENT_REJECTED` before any fetch; genuine staleness reported (ve_tower's own `DATA_STALE` gate stays authoritative). **11 A tests pass**, including: process-uptime never artificially stales the fetch (parametrised), **fake clock advances +3600 without reconstructing `TowerDependencies`** (`wall_clock_now` advances while `data_cutoff` stays pinned to `event_as_of`), historical catch-up anchors the fetch to the event's own `as_of` (never "now"), future-event refused, wall-clock rollback fail-closed, restart produces an identical fetch anchor. `event_as_of`/`data_cutoff`/`wall_clock_now` are propagated on the response/trace.
